# LEGAL | PRO — автопубликация prolg.ru

Рабочая инструкция для Артема и следующих изменений сайта. Служба и таймер установлены на сервере prolg.ru. Автоматическое получение релиза `r20261106-02` подтверждено 5 ноября 2026 года в 22:49:50 UTC: сервер применил его без ручного запуска службы, состояние `applied`, ошибок нет. Следующий релиз `r20261106-03` с точным названием `LEGAL | PRO` также автоматически применен и проверен на главной и странице `/thanks/` 5 ноября 2026 года в 22:52 UTC. Успешный коммит в GitHub сам по себе не подтверждает применение следующего релиза; результат нужно проверить на сайте.

## Что публикует механизм

Служба получает **один файл `deploy.json` из ветки `production`** репозитория `777LegalPro/legal-pro-maintenance`. Пакет содержит сами байты обновления, их SHA-256 и условия применения.

Поддерживаются:

- Полноэкранная страница технических работ и ее включение/отключение.
- Создание или замена до 50 публичных статических файлов за релиз: страницы, стили, клиентский JavaScript, данные и изображения.
- Проверка исходного содержимого, резервная копия и восстановление при неудачной записи.

Backend, серверные Python-скрипты, Nginx, systemd и административные разделы этим протоколом не обновляются. Удаление файлов схемой не предусмотрено. Механизм не превращает репозиторий в полную копию действующего приложения.

**Изменение обычного файла в репозитории не публикует его на сайт.** Обновленные байты должны попасть в `maintenance_html_base64` или соответствующий элемент `files` внутри `deploy.json`.

## Когда выполняется обновление

В установленном таймере указан `OnUnitInactiveSec=120s`: следующий опрос планируется через 120 секунд после завершения предыдущего запуска. Также заданы `AccuracySec=5s`, `RandomizedDelaySec=5s` и стартовый `OnBootSec=1min`.

Это периодический опрос, а не немедленный webhook. При сетевых ошибках применяется увеличивающаяся задержка; ограничения GitHub, `Retry-After` и время сброса rate limit учитываются. Нажатие «Commit» не гарантирует появления изменений ровно через две минуты.

## Точная схема `deploy.json`

Все поля верхнего уровня обязательны. Другие поля не принимаются.

| Поле | Тип и значение |
| --- | --- |
| `schema_version` | Целое число `1`. |
| `release_id` | Новый идентификатор, 1–80 символов из `[0-9A-Za-z._-]`. Например, `r20261106-03`. |
| `requires_release` | Идентификатор **последнего успешно примененного** релиза. `null` допускается только для первой публикации, когда успешного релиза еще нет. |
| `maintenance` | `true` — включить полноэкранную заглушку; `false` — открыть приложение после применения пакета. |
| `maintenance_html_base64` | Обычный Base64 полного HTML-документа в UTF-8. Поле обязательно и при `maintenance: false`. |
| `maintenance_html_sha256` | SHA-256 исходных байтов HTML: 64 строчные шестнадцатеричные цифры. |
| `files` | Массив от 0 до 50 объектов. Для изменения одной заглушки используется `[]`. |

Каждый объект в `files` содержит ровно четыре обязательных поля:

| Поле | Содержание |
| --- | --- |
| `path` | Путь относительно публичного `dist`, например `thanks/index.html` или `assets/site.css`. |
| `content_base64` | Base64 новых байтов файла. |
| `sha256` | SHA-256 **новых байтов**, 64 строчные шестнадцатеричные цифры. |
| `expected_sha256` | SHA-256 файла, который сейчас находится на сервере. `null` означает создание отсутствующего файла. Повторная доставка уже записанных целевых байтов допускается. |

Ограничения пакета:

- HTML заглушки — до **100 KiB**; должен быть полным документом UTF-8 с тегами `html` и `body`.
- Один новый публичный файл — до **2 MiB**; все новые публичные файлы вместе — до **4 MiB**.
- Весь JSON с Base64 — до **6 MiB**.
- Исходный файл для чтения и резервного копирования — до **8 MiB**; суммарные исходные байты транзакции — до **64 MiB**.
- Расширения: `.html`, `.css`, `.js`, `.json`, `.svg`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.ico`, `.txt`, `.xml`, `.woff`, `.woff2`, `.webmanifest`.
- Путь — до 512 символов и 32 компонентов, в нормализованном виде без повторяющихся разделителей. Абсолютные пути, `..`, скрытые компоненты, любой компонент `admin` без учета регистра, обратная косая черта, `%`, управляющие символы, символьные ссылки и файлы с несколькими жесткими ссылками не принимаются. Повторяющиеся пути также запрещены.

## Порядок релизов

Пример цепочки:

| Новый `release_id` | `requires_release` |
| --- | --- |
| `r20261106-01` | `null`, только при пустом начальном состоянии |
| `r20261106-02` | `r20261106-01` |
| `r20261106-03` | `r20261106-02` |

Идентификаторы в таблице иллюстрируют порядок, а не подтверждают текущее состояние сервера. Фактический предшественник берется из подтвержденного успешного применения.

Одинаковые `release_id` и байты JSON считаются повторной доставкой. Измененный JSON с уже примененным `release_id` отклоняется. Старый или пропущенный предшественник также приводит к отказу.

**Публикации выполнять последовательно:** подтвердить предыдущий релиз, затем отправить следующий. Служба читает текущее содержимое одного `deploy.json`; историю коммитов как очередь пакетов она не обрабатывает.

## Обновить страницу технических работ

1. Изменить локальный `maintenance.html`. Название бренда — строго `LEGAL | PRO`, с вертикальной чертой. Сохранить контакт: «По вопросам бесплатной юридической помощи» и ссылку `mailto:777@prolg.ru`.
2. Назначить новый `release_id` и указать подтвержденный `requires_release`.
3. Для проверки через публичную страницу можно обновить невидимый атрибут, например `<body data-deployment-id="r20261106-04">`.
4. Сгенерировать SHA-256 и Base64 из **тех же байтов**, которые войдут в пакет.
5. Опубликовать полученный `deploy.json` в ветке `production` и подтвердить применение.

Пример генератора для изменения только заглушки. Перед запуском заменить два идентификатора в командной строке на фактические. Последний аргумент задает состояние maintenance.

```bash
python3 - r20261106-04 r20261106-03 true <<'PY'
import base64
import hashlib
import json
from pathlib import Path
import re
import sys

release_id, previous, maintenance_arg = sys.argv[1:]
assert re.fullmatch(r"[0-9A-Za-z._-]{1,80}", release_id)
assert maintenance_arg in ("true", "false")
# Символ '-' используется только для действительно первой публикации.
requires_release = None if previous == "-" else previous
assert requires_release is None or re.fullmatch(r"[0-9A-Za-z._-]{1,80}", requires_release)
html = Path("maintenance.html").read_bytes()
html.decode("utf-8")
assert len(html) <= 100 * 1024

manifest = {
    "schema_version": 1,
    "release_id": release_id,
    "requires_release": requires_release,
    "maintenance": maintenance_arg == "true",
    "maintenance_html_base64": base64.b64encode(html).decode("ascii"),
    "maintenance_html_sha256": hashlib.sha256(html).hexdigest(),
    "files": []
}
Path("deploy.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2) + "\n",
    encoding="utf-8"
)
print(release_id, manifest["maintenance_html_sha256"])
PY
```

Для публичных файлов перед записью JSON добавить объекты в `manifest["files"]`. Их `content_base64` и `sha256` вычисляются аналогично из новых байтов. `expected_sha256` должен относиться к фактическому текущему файлу на сервере; копия из другой ветки или прежней заготовки сайта не подтверждает этот хеш.

Команды и произвольные URL скачивания в пакет не включаются: runner не выполняет инструкции из JSON и не загружает перечисленные там адреса.

## Включить или отключить полноэкранную заглушку

Для переключения создать **новый релиз** с правильным `requires_release`, актуальными полями HTML и `files: []`:

- `maintenance: true` — сайт закрывается полноэкранной страницей.
- `maintenance: false` — после применения пакета открывается приложение.

При обновлении публичных файлов runner временно включает maintenance до их записи и проверки. Запрошенное итоговое состояние устанавливается последним.

**Прежний верхний баннер остается в приложении.** Отключение полноэкранной заглушки возвращает текущее приложение, в котором ранее был добавлен верхний баннер «Технические работы». `maintenance: false` этот баннер не удаляет; его снятие требует отдельного изменения файлов приложения.

## Откат новой публикацией

Чтобы вернуть прежний вид после успешного релиза:

1. Взять прежние проверенные байты HTML и измененных файлов.
2. Назначить **новый** `release_id`; в `requires_release` указать текущий успешный релиз.
3. Для возвращаемых публичных файлов указать в `expected_sha256` хеш их текущей версии, а в `sha256` — хеш возвращаемых байтов.
4. Указать требуемое итоговое состояние `maintenance` и опубликовать пакет.

Старый `deploy.json` нельзя просто вернуть целиком: его идентификатор, предшественник и ожидаемые исходные хеши могут уже не соответствовать серверу. Откат существующего файла — это его замена прежними байтами. Удаление созданного файла требует отдельного административного действия.

При ошибке самой транзакции runner пытается восстановить свои изменения автоматически. Заглушка остается включенной до завершения восстановления. Если обнаружена чужая правка, она сохраняется, а незавершенная транзакция и maintenance остаются для разбора; новая публикация не отменяет такую защиту.

## Подтверждение результата после установки

Установленная конфигурация использует:

| Объект | Название или путь |
| --- | --- |
| Служба | `legal-pro-deploy.service` |
| Таймер | `legal-pro-deploy.timer` |
| Конфиг | `/etc/legal-pro-deploy.json` |
| Runner | `/usr/local/lib/legal-pro-deploy/runner.py` |
| Состояние | `/var/lib/legal-pro-deploy/state.json` |
| Резервные копии | `/var/lib/legal-pro-deploy/backups/` |
| Полноэкранная страница | `/var/www/legal-pro-maintenance/maintenance.html` |
| Флаг maintenance | `/var/www/legal-pro-maintenance/enabled` |

После установки локальное состояние читается без сетевого запроса:

```bash
sudo -u legal-pro-deploy /usr/bin/python3 /usr/local/lib/legal-pro-deploy/runner.py --status
```

Для подтверждения нужны `status: "applied"`, ожидаемый `release_id`, соответствующий хеш manifest и проверка публичного результата. Если в HTML использован `data-deployment-id`, его значение позволяет сверить именно опубликованную заглушку. При включенной заглушке Nginx отдает ее со статусом HTTP 503 на главной, внутренних разделах и неизвестном адресе.

`legal-pro-deploy.service` имеет тип `oneshot`: между опросами сама служба может быть неактивна. Периодическое выполнение обеспечивает активный таймер. Диагностика после установки:

```bash
systemctl status legal-pro-deploy.timer
systemctl show legal-pro-deploy.service -p Result -p ExecMainStatus
journalctl -u legal-pro-deploy.service -n 30 --no-pager
```

При необходимости оператор может запустить один обычный опрос командой `sudo systemctl start legal-pro-deploy.service`; предусмотренный backoff при этом сохраняется.
